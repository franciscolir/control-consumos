# ESPECIFICACION.md — Fuente de verdad del proyecto

> **Proyecto:** Control de Consumos de Agua y Electricidad en Establecimientos Educacionales
> **Versión:** 0.1.0 (base inicial)
> **Naturaleza:** Aplicación 100% local, sin dependencia de Internet ni servicios en la nube.
> **Estado:** Documento vivo. Toda decisión técnica debe reflejarse aquí antes de programarse.

---

## 1. Propósito

Construir una aplicación de escritorio web, **100% local**, que permita a una institución educativa:

- Registrar boletas de agua y electricidad de múltiples establecimientos.
- Validar automáticamente lecturas, fechas y montos.
- Extraer datos de boletas mediante OCR local.
- Calcular métricas y detectar consumos atípicos.
- Generar informes exportables (Excel, CSV, PDF).
- Mantener trazabilidad completa de correcciones y alertas.

**No es** un simple registro de boletas: es un sistema de control, validación y análisis.

---

## 2. Principios rectores

1. **100% local.** Sin CDN, sin cuentas, sin servicios externos. Todo funciona sin Internet.
2. **Integridad del dato primero.** Las lecturas y su trazabilidad son más importantes que las métricas.
3. **Modelo medidor-céntrico.** El consumo se asocia al medidor, no al establecimiento.
4. **Validaciones no bloqueantes.** Se advierte, no se impide registrar excepciones justificadas.
5. **Trazabilidad total.** Todo cambio queda registrado. Las alertas conservan historial.
6. **Modularidad.** Interfaz, lógica de negocio, validaciones y datos separados.
7. **OCR con confirmación humana.** Ningún dato extraído por OCR entra sin revisión.

## 3. Stack tecnológico

| Capa | Tecnología | Restricción |
|---|---|---|
| Servidor | Node.js + Express | Local, puerto 3000 por defecto |
| Base de datos | SQLite | Archivo local en `/data` |

| OCR | Tesseract.js | Ejecutado en Node.js, modelos locales en `/data/ocr/tessdata` |
| Preprocesamiento de imagen | Sharp | Local: rotar, escalar, binarizar |

## 5. Sistema de validaciones

Se ejecutan automáticamente al crear o modificar un registro. **Nunca bloquean el guardado**; generan entradas en `validaciones`.

| Código | Validación | Condición | Severidad |
|---|---|---|---|
| V01 | Fechas invertidas | `fecha_fin < fecha_inicio` | error |
| V02 | Duración inusual | días fuera de [25, 35] | advertencia |
| V03 | Lectura regresiva | `lectura_actual < lectura_anterior` | advertencia |
| V04 | Discrepancia de consumo | \|calculado − facturado\| > 5% | advertencia |
| V05 | Continuidad | `lectura_anterior` ≠ última `lectura_actual` del servicio | advertencia |
| V06 | Duplicado | mismo servicio + folio + período | error |
| V07 | Consumo cero | `lectura_actual == lectura_anterior` | info |
| V08 | Consumo atípico | Z-score \|Z\| > umbral **o** fuera de IQR **o** desvío vs. mismo mes histórico | advertencia |
| V09 | Montos inconsistentes | `total` ≠ suma de conceptos (±tolerancia) | advertencia |
| V10 | Período superpuesto | solapamiento con otro registro del mismo servicio | error |
| V11 | Confianza OCR baja | `confianza_global < 70` | advertencia |
| V12 | Campo crítico no detectado | Falta lectura, fecha o monto | error |
| V13 | Valor OCR inconsistente | Valor extraído no pasa V01–V10 al compararse | advertencia |
| V14 | Documento duplicado | Hash del archivo ya existe | advertencia |

**Excepciones legítimas:** cambio de medidor, reinicio, ajuste tarifario. Se registran vía `tipo_lectura` + `observaciones` + `historial_cambios`.

**Regla de oro OCR:** ningún dato extraído se guarda en `registros` sin confirmación humana en la primera versión.

Flujo OCR:
Subir imagen/PDF → OCR → Revisión humana → Confirmar → registros

## 6. Motor de métricas

### 6.1 Indicadores

| Indicador | Fórmula |
|---|---|
| Consumo total | Σ consumo del período |
| Promedio mensual | Consumo total / meses con registro |
| Promedio diario | Consumo / días facturados |
| Variación mensual | (actual − anterior) / anterior × 100 |
| Variación interanual | (mes actual − mismo mes año anterior) / mismo mes año anterior × 100 |
| Costo unitario | monto consumo / consumo |
| Costo total | Σ montos |
| Desviación estándar | σ poblacional de la serie |
| Puntaje Z | (x − μ) / σ |

### 6.2 Detección de atípicos (3 métodos, todos activos)

1. **Z-score:** alerta si \|Z\| > umbral (default 2.5, configurable).
2. **IQR:** atípico si `x < Q1 − 1.5·IQR` o `x > Q3 + 1.5·IQR`.
3. **Comparación estacional:** vs. mismo mes de años anteriores.

**Regla:** cada alerta debe indicar **qué método la originó**.

### 6.3 Métricas consolidadas

- Totales por tipo de servicio (agua / electricidad).
- Promedios por establecimiento y por servicio.
- Ranking de mayor variación mensual.
- Distribución de consumos.
- Comparación interanual.
- Conteo de registros con error / advertencia / pendientes.
- Indicadores normalizados (m³/alumno, kWh/m²) **si hay datos**.

> El OCR no afecta métricas. Sí afecta la calidad del dato de entrada, por eso su salida debe pasar por validaciones V01–V14.

### 7.1 Vista OCR (nueva pantalla)

1. **Zona de carga:** arrastrar imagen (JPG, PNG) o PDF.
2. **Preview del documento** a la izquierda.
3. **Panel de campos detectados** a la derecha, con:
   - Valor extraído.
   - Confianza (barra de color: verde >85, amarillo 70–85, rojo <70).
   - Botón "editar".
4. **Selección de plantilla** (proveedor) antes de procesar, si existe.
5. **Botón "Confirmar y crear registro"** (solo habilitado si no hay errores críticos).

## 10. Flujo de ejecución

### 10.1 General

1. `npm install`
2. `npm start`
3. Abrir `http://localhost:3000`
4. La base de datos se crea/migra automáticamente al iniciar si no existe.

### 10.2 Flujo OCR
Usuario sube boleta (imagen o PDF).

Se guarda en /data/documentos con hash.

Se crea ocr_proceso (estado: pendiente).

Preprocesamiento (Sharp): corrección de orientación, escala, contraste.

Si es PDF con texto → pdf.adapter extrae directo.
Si es PDF escaneado o imagen → Tesseract.js.

parser.js aplica regex + plantilla del proveedor.

Se calcula confianza por campo.

Se ejecutan validaciones V11–V14.

Usuario revisa en pantalla OCR, corrige lo necesario.

Al confirmar → se crea registro + detalle_boleta.

Se ejecutan validaciones V01–V10 sobre el registro confirmado.

## 15. Consideraciones técnicas OCR

### 15.1 Formatos soportados

- **Imágenes:** JPG, PNG, TIFF (entrada directa a Tesseract).
- **PDF con texto:** extracción directa (más rápido y preciso).
- **PDF escaneado:** se convierte a imagen por página y se procesa con Tesseract.

### 15.2 Idiomas

- Modelos `spa.traineddata` y `eng.traineddata` incluidos en `/data/ocr/tessdata`.
- Configuración por defecto: `spa+eng` (las boletas chilenas suelen tener ambos).

### 15.3 Preprocesamiento (mejora notable de precisión)

1. Corregir orientación (EXIF + detección automática).
2. Escalar a 300 DPI si es menor.
3. Convertir a escala de grises.
4. Binarizar con umbral adaptativo.
5. Eliminar ruido (opcional, modo conservador).

### 15.4 Estrategia de extracción de campos

- **Fechas:** regex de formatos chilenos (`dd/mm/yyyy`, `dd-mm-yyyy`, `dd de mes de yyyy`).
- **Lecturas:** buscar etiquetas ("Lectura actual", "Lectura anterior") y capturar número cercano.
- **Montos:** patrón `$` + número con separador de miles.
- **Folio:** etiquetas ("Folio", "N° boleta", "Nº documento").
- **Período:** combinación de fecha inicio + fecha fin.

### 15.5 Umbrales de confianza (configurables)

- `> 85`: campo aceptado automáticamente (aún requiere confirmación global).
- `70–85`: resaltado en amarillo, revisar.
- `< 70`: resaltado en rojo, edición obligatoria.

### 15.6 Manejo de errores

- Si Tesseract falla → `ocr_proceso.estado = 'error'`, se guarda log.
- Si no se detecta ningún campo crítico → se ofrece entrada manual.
- Nunca se pierde el archivo original.

### 15.7 Rendimiento

- Procesamiento **asíncrono**: la UI muestra progreso, no bloquea.
- Boleta típica (1 página): 3–8 segundos en CPU moderna.
- Límite de tamaño de archivo: 20 MB configurable.
